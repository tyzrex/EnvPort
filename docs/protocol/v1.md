# EnvPort protocol v1 (experimental)

The implementation is new; there are no supported predecessor releases. Golden compatibility fixtures live in `testdata/protocol/v1`. Their checked-in private identity is **synthetic test material**, never a real vault key. Regenerate only when deliberately defining a new fixture, using `go run ./internal/goldenfixture`; ordinary tests never regenerate it.

## Logical namespace

```
<profile-prefix>/v1/vaults/<32-lowercase-hex-vault-id>/
  refs/main
  snapshots/<32-lowercase-hex-snapshot-id>.age
  blobs/<32-lowercase-hex-blob-id>.age
```

All three object kinds are binary age v1 files encrypted to a vault-specific X25519 recipient. Each age stream uses independently generated randomness. The filesystem adapter stores the logical keys and ciphertext bytes in `objects.db`; an S3 profile stores each as an actual object. No raw hashes or user paths appear in storage keys or custom metadata. Ciphertext lengths, ETags, request timing and namespace are visible to storage. There is no padding or compression.

No public protocol.json or remote key envelope namespace is written in this implementation. Version checking occurs after authenticating the reference and manifest. Recovery and pairing artifacts are separately transported files, not silently uploaded to a provider. These are deliberate differences from the guide's illustrative layout.

## Authenticated structures

The encrypted reference contains `schema_version:1`, `vault_id`, `snapshot_id`, `generation`. The encrypted manifest contains `schema_version`, `vault_id`, `snapshot_id`, at most one `parent_snapshot_ids`, monotonically increasing `generation`, `author_device_id`, UTC `created_at`, `projects`, optional `required_features`. See `pkg/protocol/v1.go` and `testdata/protocol/v1/manifest.json` for exact field names.

Project records contain `project_id`, optional `canonical_remote`, `files`. File records contain stable `file_id`, portable `relative_path`, random `blob_id`, encrypted `content_sha256`, `plaintext_length`, optional `deleted`. Tombstones carry no live blob. V1 restores are limited to `.env` / `.env.*` filenames outside `.git`; no arbitrary executable/hook restoration is supported.

Reject unknown schemas/required features/JSON fields, malformed IDs, duplicate IDs, case-folded duplicate paths, nonportable paths and oversized objects. Limits: 8 MiB per plaintext file, 16 MiB per ciphertext object, 10,000 files per manifest, 10,000 history entries per traversal. No streaming multipart or huge-vault claim applies. Recovery scrypt work is capped at factor 18 to bound hostile-envelope costs.

Generation one has no parent. Each following committed generation names exactly one predecessor. Returning clients walk authenticated parents to the locally trusted checkpoint and reject gaps or rollback. A new device cannot establish newest-history freshness from an untrusted bucket alone.

## Commit and crash behavior

1. Authenticate head and ancestry; preserve observed storage ETag.
2. Create a local staged operation and per-file digest journal.
3. Encrypt/create immutable changed blobs and a complete new manifest.
4. Encrypt the new reference and conditionally create (`If-None-Match:*`) or replace (`If-Match:<ETag>`) the head.
5. Only after success, transactionally record common baselines, checkpoint and committed operation.
6. A failed CAS returns a typed precondition error. The caller must obtain a new plan; it never retries the old reference blindly.
7. An ambiguous write rereads the authenticated head. If its own transaction is observed it records success; otherwise the journal remains pending for `sync` reconciliation. Reconciliation determines whether a staged manifest is in committed ancestry; uncommitted uploads become abandoned.

All snapshot history is retained. Missing local files do not create tombstones. No garbage collection is enabled; `prune --dry-run` lists unreferenced objects only. An orphan is tolerable; a committed manifest with a missing or invalid blob is a restore/doctor failure.

## Key envelopes and enrollment

Local `key-<vault-id>.age` contains age-scrypt-encrypted JSON `{version:1,vault_id,identity}`. The portable recovery bundle has the same plaintext schema encrypted with an independent recovery passphrase. The actual age identity is the shared vault decryption secret. An account, storage credential or device ID alone cannot decrypt it.

`device.age` separately encrypts the installation's device ID, X25519 private encryption identity and Ed25519 signing key. Join requests contain version, vault/device binding, random nonce, public encryption/signing keys, expiration and Ed25519 signature. Request signatures cover canonical Go JSON with the signature omitted; fingerprint = SHA-256 of these signed fields. Approvals are Ed25519 signed grants containing the precise request fingerprint, vault/device binding, expiry, issuer public key and vault identity, entirely encrypted with age to the requesting device's public key. The issuer fingerprint must be authenticated out of band. Pending requests are persisted and consumed transactionally; expired/replayed/foreign-device grants are rejected.

These JSON signing conventions are Go v1 contracts; another-language implementation needs byte-for-byte canonical encoding compatibility. Vault manifests themselves are age-authenticated, not separately device-signed. Anyone with the shared root can forge authors. No cryptographic revocation/rotation or team authorization is shipped.

## Migration

Never reinterpret AES prototype bytes as age. The supplied starter has a read-only EVP1 AES-GCM reader and original-client-generated compatibility fixtures. `migrate-legacy` authenticates a selected source snapshot, creates a new independent v1 vault/recovery bundle, immediately re-encrypts bytes in memory, reads back/verifies all new blobs and manifest, atomically publishes the new head and writes a receipt. Source keys/config/snapshots remain unchanged. See `docs/MIGRATION.md`; future incompatible writers require a new protocol/version and explicit migration.
